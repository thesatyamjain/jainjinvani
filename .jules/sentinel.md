## 2024-05-14 - Vite Environment Variable Leak
**Vulnerability:** The VITE_ADMIN_PASSWORD was being read as a plaintext environment variable. In Vite, any environment variable prefixed with VITE_ is statically replaced with its value during the build process, thereby exposing the plaintext password to the public bundle.
**Learning:** Client-side bundles should never include plaintext passwords or secrets as environment variables, even if they are only used to verify an input on the client-side. The public bundler will expose them.
**Prevention:** Always hash the password and provide the hash as the environment variable (e.g., VITE_ADMIN_PASSWORD_HASH), then check if the hash of the user input matches the provided hash.
## 2024-05-24 - Hardcoded Client-side 2FA Secret
**Vulnerability:** A hardcoded `MASTER_2FA_SECRET` base32 string was directly committed and exported in the client-side code (`src/pages/AdminLogin.tsx`). Any attacker who reads the source code could view this string and use it to generate their own valid 2FA TOTP codes, entirely bypassing the 2FA layer.
**Learning:** For client-side-only architectures where authentication logic relies solely on the browser's Web Crypto API, secrets that need to be known by the client to generate/verify tokens (like TOTP seeds) must never be hardcoded into the source bundle. They must be dynamically generated on the client per device using cryptographically secure PRNGs (`window.crypto.getRandomValues`) and stored locally (e.g. `localStorage`).
**Prevention:** Remove hardcoded client-side secrets. Use `crypto.getRandomValues` to generate them and persist locally. If removing a legacy hardcoded fallback, gracefully handle backward compatibility by checking existing state and prompting users to re-setup their security rather than locking them out.
